Papyrus v2.5.0 Planejamento de mensuração e mapas de coleta para GA4

Visão geral

Um canvas que termina em contrato de coleta

O Papyrus é uma ferramenta de planejamento de mensuração para o Google Analytics 4. Você desenha a arquitetura de dados de uma tela — print de referência, pins nos pontos de interação, cards de evento com parâmetros tipados — e a mesma página vira um JSON que o time de engenharia implementa sem redigitar nada.

O problema que ele resolve

Planejamento de mensuração costuma morar em três lugares ao mesmo tempo: uma planilha com os eventos, um Figma com as telas anotadas e um ticket com a descrição do gatilho. Os três divergem na primeira semana. O Papyrus junta os três em um artefato só — o mapa é o desenho, a especificação e o contrato — e faz o caminho terminar em um arquivo único, versionado, no Google Cloud Storage.

A consequência prática: o parâmetro que o analista digitou no card é literalmente o mesmo texto que aparece no dataLayer.push gerado para o desenvolvedor, e o mesmo que sai no JSON do bucket. Não há transcrição no meio, então não há erro de transcrição.

O ciclo completo

  1. DesenharCole o print da tela, marque os pontos com pins e crie os cards de evento no canvas infinito.
  2. EspecificarNo inspetor, cada card recebe nome, tipo, plataformas, gatilho, governança e as tabelas de parâmetros tipados.
  3. ValidarO validador roda continuamente: snake_case, nomes reservados do GA4, limites da plataforma, parâmetro duplicado, event_id repetido.
  4. ConsolidarO Dicionário Global varre o workspace inteiro e mostra o mesmo parâmetro declarado com tipos diferentes — o erro de schema que sai caro no BigQuery.
  5. EntregarO card gera dataLayer.push, gtag() ou JSON Schema; o botão Exportar publica o contrato do workspace inteiro no bucket.

A stack, e o que ela não tem

Node com Express no servidor, JavaScript com módulos ES nativos no navegador e Konva para o canvas. Não há React, bundler, TypeScript nem etapa de build: o navegador carrega os arquivos .js como estão no disco. npm start e a ferramenta está no ar em cerca de um segundo.

Nota de projeto

A única dependência de runtime obrigatória é o express. O konva é servido a partir do node_modules pelo próprio servidor, então a ferramenta funciona offline, e o @google-cloud/storage é carregado por import dinâmico apenas na hora do upload — sem ele, tudo continua funcionando menos o botão Exportar.

Como a credencial é guardada

A chave privada é gravada em _system/gcs-service-account.json e o gcs.json guarda só o caminho dela — a chave nunca entra no arquivo de configuração e nunca volta para o navegador. A API devolve apenas o booleano hasCredential. Se a pasta papyrus for versionada, adicione _system/gcs-service-account.json ao .gitignore.

Quando a porta está ocupada

O servidor trata EADDRINUSE explicitamente, porque o caso quase sempre é o próprio Papyrus já rodando em outra janela de terminal. Em vez de um stack trace do Node, ele imprime o que fazer:

Como usar

Do print de tela ao JSON no bucket

A ferramenta tem quatro abas — Canvas, Grupos de Parâmetros, Dicionário Global e Configurações — e um fluxo recomendado que atravessa as três primeiras.

Fluxo recomendado

  1. Crie a páginaPastas e páginas na barra lateral são pastas e arquivos de verdade no disco.
  2. Cole o print Ctrl+VA imagem vai para _assets/ e o documento guarda só a URL.
  3. Marque os pontos PPins numerados sobre os elementos que disparam eventos.
  4. Crie os cards ECada card já nasce com um event_id preenchido.

O Card de Evento

É o elemento central. No canvas ele é o resumo; no inspetor, a ficha completa — cerca de vinte campos mais três tabelas de parâmetros. A cor da tarja codifica o tipo, e a codificação é funcional, não decorativa:

TipoidCorQuando usar
Viewview#1A73E8Visualização de tela ou conteúdo.
Interactioninteraction#188038Ação deliberada do usuário. É o padrão.
Ecommerceecommerce#F9AB00Ativa a tabela items[] com os 18 parâmetros padrão do GA4.
Automaticautomatic#A142F4Evento coletado automaticamente. É o único tipo que pode usar nome reservado.

Três escopos de parâmetro convivem no card: Parâmetros de Evento, Propriedades de Usuário e Parâmetros de Item — este último só aparece em cards Ecommerce. Cada parâmetro tem nome, tipo, obrigatoriedade, valor de exemplo e descrição.

O event_id

Toda coleta precisa de uma chave que amarre o planejamento ao dado que chega no GA4. O Papyrus cria essa chave sozinho, em três partes separadas por hífen:

formato do event_id
d102111109101 - p1757203200 - 6k3f9zq
│                │             └── 6 + sufixo aleatório de 6 caracteres
│                └──────────────── p + timestamp atual em segundos
└───────────────────────────────── d + código ASCII de cada letra da pasta

Os códigos ASCII vão sempre com três dígitos e zero à esquerda. Sem esse preenchimento, "AB" (65, 66) e "6566" produziriam a mesma string e o prefixo deixaria de identificar a pasta. Página na raiz usa papyrus como pasta.

Copiar nunca copia a chave

Colar cards, duplicar com Ctrl+D e duplicar a página inteira geram um event_id novo para cada cópia. Dois cards com o mesmo id virariam o mesmo evento no GA4 — e o validador trata isso como erro, não como aviso.

Nomes únicos no workspace

Dentro de papyrus não existem dois nomes iguais: nem duas páginas, nem duas pastas, nem uma pasta e uma página compartilhando o nome. A regra vale para o workspace inteiro, não para a pasta onde o item nasce, e a comparação ignora a caixa da letra.

O motivo está no exportador: o JSON usa o nome da página como chave raiz, e chave de objeto não se repete. Com dois nomes iguais, uma página sobrescreveria a outra e o contrato chegaria ao bucket com eventos faltando, sem nenhum aviso.

Nada é renomeado em silêncio

Antes, um nome ocupado virava home (2). Hoje a tentativa é recusada com uma mensagem que diz qual item usa o nome e em que pasta ele está. Vale para criar página, criar pasta, renomear, mover e importar. Duplicar uma página pede o nome da cópia, já preenchido com a primeira sugestão livre.

Grupos de Parâmetros

Um grupo é um conjunto nomeado de parâmetros que se repetem — "Contexto de Página", "Identificação do Usuário", "Dados do Produto". O card importa o grupo inteiro de uma vez, e é assim que o mesmo parâmetro mantém nome e tipo iguais no workspace todo. O importador recalcula conflitos em tempo real e só libera a importação quando não há colisão com o que o card já tem.

Dicionário Global

Consolida o workspace inteiro em três visões: todo evento e onde ele mora, os parâmetros únicos com o de-para dos eventos que os usam, e os conflitos de tipo — o mesmo parâmetro declarado como string em uma página e int em outra. Esse é o erro que só aparece depois, quando o dado já está no BigQuery. Fecha com a lista de event_id repetido entre páginas, colisão que nenhuma página consegue enxergar sozinha.

Arquitetura

Como funciona por dentro

Duas metades com um contrato estreito entre elas: um servidor Express que só sabe ler e gravar arquivos, e um front-end de módulos ES que só fala com ele por fetch em JSON.

O caminho de um dado

Toda alteração no canvas passa por commit(), que empilha o snapshot de undo e agenda o auto-save. O disco é a fonte da verdade; o bucket recebe só o contrato consolidado.

O servidor

server/index.js monta quatro coisas: os estáticos de public/, o Konva servido do node_modules (para funcionar offline), o diretório papyrus/ exposto em /papyrus para as imagens do canvas, e os três routers da API. Fecha com um handler de erro que traduz qualquer exceção em { error } usando err.status. É por isso que lançar um erro com status em qualquer lib/ chega na interface como um toast legível.

CamadaResponsabilidadeNão faz
routes/Ler o request, chamar a lib, responder.Nenhuma regra de negócio própria.
lib/Regras: caminhos, formato de arquivo, nomes, cores, GCS.Não conhece Express nem req/res.

A regra de segurança do formato

Um arquivo só é renderizado se a raiz do JSON contiver "json-type": "papyrus". Todo o resto é ignorado. .json sem a assinatura aparece esmaecido na barra lateral, marcado como ignorado, e não abre; na importação é recusado com o motivo.

A segunda barreira é de caminho: resolveInPapyrus() é o único lugar que converte o caminho relativo da API em caminho absoluto, e ele rejeita qualquer resultado que caia fora da raiz. A API nunca devolve caminho absoluto nem expõe a estrutura do host — o navegador de diretórios do sistema operacional foi removido de propósito, para a ferramenta poder rodar em servidor compartilhado.

Histórico e auto-save

commit() é o único caminho de mutação. Ele empilha um snapshot inteiro do documento (não comandos invertidos), aplica a mutação em uma cópia, avisa os assinantes e agenda a gravação com 700ms de debounce. O limite é de 80 passos.

Snapshot inteiro é mais caro do que comando invertido, e a escolha é consciente: uma página típica tem dezenas de elementos, não milhares, e o modelo de comandos é bem mais fácil de quebrar. Trocar de página, exportar ou apertar Ctrl+S chama flushSave(), que cancela o debounce e grava na hora.

O 409 do export

O export é recusado quando algum event_id falta ou se repete. A interface já checa isso antes de habilitar o botão, mas a garantia mora no servidor: o arquivo no bucket é lido como verdade pelo time de engenharia, e um id repetido faz dois eventos diferentes chegarem como o mesmo no GA4. A resposta traz problems com a página, o evento e o tipo da falha.

Decisões técnicas

Por que o código é assim

Os trechos que parecem estranhos até você saber o que eles evitam. Cada um tem uma falha real por trás — abra para ver o código e o motivo.

Arquitetura e formato

▸ Express local em vez de Electronserver/index.js

A ferramenta precisa de acesso real ao sistema de arquivos: criar pastas, ler e gravar JSON. Um front-end puro no navegador não teria isso. Entre Electron e um servidor Node local, o servidor venceu por três motivos — sobe em cerca de um segundo sem build step, roda em qualquer máquina com Node, e permite abrir o mapa em várias abas, em dois monitores, ou compartilhar na rede interna do time.

O front-end e a API já estão desacoplados, então nada impede empacotar como Electron depois.

▸ A assinatura "json-type": "papyrus"lib/papyrus.js

A pasta de trabalho é apontável pelo usuário via PAPYRUS_DIR e pode ser um diretório cheio de outros arquivos. Renderizar qualquer .json que aparecesse seria uma porta aberta para tratar dado de outro sistema como documento de canvas.

A verificação é uma linha, e é a fundação de tudo: readDocIfValid() devolve null em qualquer falha — arquivo ilegível, JSON quebrado ou assinatura ausente — e nunca lança. Quem chama decide o que fazer com o null.

server/lib/papyrus.js
export function isPapyrusDoc(doc) {
  return Boolean(doc) && typeof doc === 'object' && doc['json-type'] === PAPYRUS_TYPE;
}
▸ Imagens fora do JSONroutes/assets.js

Um print de tela em base64 embutido no documento transformaria um arquivo de 8 KB em um de 3 MB, ilegível para humanos e péssimo em diff do Git. As imagens vão para _assets/<data>/<uuid>.<ext> e o documento guarda só a URL.

O agrupamento por dia não é estética: é o que torna possível uma limpeza manual futura sem precisar cruzar cada arquivo com cada documento.

▸ Cor de pasta fora das pastas do usuáriolib/folder-colors.js

As cores vivem em _system/folder-colors.json, indexadas pelo caminho da pasta. Cor é assunto de interface, não conteúdo do mapa de coleta — deixá-la ali mantém os JSONs de página limpos e fáceis de revisar em pull request.

O preço é moveFolderColors(): renomear ou arrastar uma pasta muda o caminho dela e o de todas as subpastas, então as chaves precisam ser reapontadas em conjunto. Sem isso, a cor se perderia a cada arrastar e soltar.

Nomes e identidade

▸ Por que uniquePath foi removidolib/paths.js

A função resolvia colisão de nome acrescentando (2) ao final. Parecia gentil, e era exatamente a forma mais fácil de acabar com duas páginas quase idênticas no workspace sem ninguém perceber — home e home (2), cada uma com metade dos eventos.

Hoje colisão vira erro 409 com o nome e o lugar do que já existe. O comentário que ficou no lugar da função existe para ninguém reintroduzi-la por conveniência.

▸ Unicidade global, e não por pastalib/names.js

O JSON exportado usa o nome da página como chave raiz, e chave de objeto não se repete. Ou o arquivo carrega o caminho completo de cada página, ou o nome é único de verdade. A escolha foi a segunda: o nome vira identificador, e a colisão morre na criação, quando ainda há alguém na tela para resolver.

A comparação ignora a caixa da letra porque o disco do Windows já trata Frutas e frutas como o mesmo arquivo, e duas páginas separadas só pela caixa seriam indistinguíveis na árvore lateral.

server/lib/names.js
export function findConflict(taken, name, ignorePath = null) {
  const hit = taken.get(normalizeName(name));
  if (!hit) return null;
  // O próprio item não conta: trocar "abacate" por "Abacate"
  // precisa continuar sendo uma renomeação válida.
  if (ignorePath && hit.path === toApiPath(ignorePath)) return null;
  return hit;
}
▸ A regra existe duas vezes, de propósitonames.js + sidebar.js

O servidor é a autoridade e recusa de novo tudo o que passar pela interface. A cópia da regra na barra lateral existe só pelo aviso: sem ela, o modal fecharia, o toast de erro apareceria e o nome digitado se perderia — que é justamente o texto que a pessoa precisa ter em mãos para corrigir.

As duas normalizeName carregam um comentário apontando uma para a outra. Divergirem faria a interface liberar um nome que o servidor recusa em seguida.

▸ O padStart(3, '0') do event_idpublic/js/models.js

O prefixo do id é o código ASCII de cada letra da pasta. Sem preencher com zero à esquerda, "AB" (65, 66) viraria 6566 — e uma pasta literalmente chamada 6566 produziria a mesma string. O prefixo deixaria de identificar a pasta.

O NFD antes do filtro separa o acento da letra, então Ação vira Acao em vez de perder caracteres inteiros.

public/js/models.js
const ascii = [
  ...String(folderName || 'papyrus')
    .normalize('NFD')
    .replace(/[^\x20-\x7E]/g, ''),
]
  .map((char) => String(char.charCodeAt(0)).padStart(3, '0'))
  .join('');
▸ O Set em renewEventIdspublic/js/models.js

Cópia de card é cópia de tudo, menos da chave que identifica a coleta. Mas duplicar dez cards de uma vez acontece todo no mesmo segundo, e o timestamp do id é idêntico para todos — aí o sufixo aleatório de seis caracteres é a única coisa separando um id do outro.

O Set garante que nenhum id se repita dentro do próprio lote, sorteando de novo quando cai um repetido.

Canvas e desempenho

▸ O fingerprint do render incrementalcanvas/stage.js

Reconstruir o palco inteiro a cada tecla digitada no inspetor era a maior fonte de travamento em mapas grandes. Cada nó Konva guarda o JSON do elemento que o gerou; se o fingerprint não mudou, o nó é reaproveitado como está.

O detalhe que não é óbvio: imagem tem estado fora do elemento. Com o mesmo objeto, o visual muda quando o arquivo termina de carregar e o placeholder vira bitmap — por isso o estado do carregamento entra no hash.

public/js/canvas/stage.js
const loadedSuffix = el.type === 'image' && imageCache.has(el.url) ? '|loaded' : '';
const fp = JSON.stringify(el) + loadedSuffix;
const cached = nodeCache.get(el.id);

if (cached && cached.fp === fp) continue; // nó reaproveitado como está
▸ Conectores sempre reconstruídosstage.js + geometry.js

Todo elemento passa pelo diff, menos o conector. Ele depende da posição e da altura medida dos elementos que liga, e a altura de um card de evento só é conhecida depois de desenhado — fica no sizeCache, preenchido no render. São poucos e baratos, então reconstruir sempre custa menos do que rastrear a dependência.

Durante um arrasto nada é reconstruído: o Konva move os nós e só as linhas são recalculadas em tempo real, com as posições vivas dos nós, não com as do documento.

▸ A ordem Z realinhada à mãocanvas/stage.js

layer.add() de um nó que já é filho do layer é no-op no Konva. Como o diff reaproveita nós antigos, a pilha de desenho deixaria de refletir a ordem do array de elementos. Por isso a ordem é realinhada explicitamente com moveToTop(), elementos primeiro e conectores depois, para as setas ficarem sempre por cima.

▸ Os três cuidados do exportPNGcanvas/stage.js

1. A camada de overlay — transformer, marquee, preview de conector — é escondida, senão vaza para a imagem final.

2. O fundo vai desenhado como um retângulo de verdade: o toDataURL do Konva não aceita cor de fundo, e sem isso o PNG sairia transparente.

3. O palco é redimensionado temporariamente para cobrir toda a área exportada. Os canvases das camadas têm o tamanho da viewport visível, e sem esse passo tudo o que estivesse fora da janela sairia cortado.

▸ Curva de Bézier em vez de linha retacanvas/geometry.js

Os pontos de controle saem perpendiculares ao lado ancorado. É o que produz a curva em S: a linha nasce da borda do card e chega suave no destino, em vez de cortar o elemento na diagonal. O par de âncoras é escolhido pela menor distância entre os quatro lados de cada elemento — daí a sensação de conector magnético mesmo depois de arrastar os cards.

Estado e interface

▸ A janela de 1200ms do undopublic/js/store.js

Digitar o nome de um evento gera dezenas de commits, e todos precisam caber em um único passo de Ctrl+Z. Commits consecutivos com a mesma coalesceKey dentro da janela não empilham snapshot novo.

O lastCommit é zerado depois de um undo. Sem esse reset, um commit agrupado logo em seguida não empilharia snapshot, e o Ctrl+Z seguinte não teria para onde voltar.

▸ Snapshot inteiro em vez de comandos invertidospublic/js/store.js

Um sistema de comandos invertidos seria mais econômico em memória, e bem mais fácil de quebrar: cada tipo de mutação precisaria da sua inversa correta. Nesta escala a economia não paga — uma página típica tem dezenas de elementos, não milhares — e o limite de 80 passos fecha a conta.

▸ Viewport fora do históricopublic/js/store.js

Zoom e pan são gravados no documento, para a página reabrir onde você parou, mas passam por saveViewport() e não por commit(). Se entrassem no histórico, Ctrl+Z desfaria um scroll em vez da última edição de verdade.

▸ O selfUpdate do inspetorpanels/inspector.js

O painel é HTML reconstruído a cada render. Se uma tecla digitada em um campo disparasse o re-render do próprio painel, o input perderia o foco no meio da palavra.

Por isso alteração que nasce no inspetor marca selfUpdate e re-renderiza apenas o canvas. O card no palco acompanha a digitação; o painel fica quieto.

▸ Validação com 250ms de atrasopublic/js/main.js

O validador percorre todos os cards, todos os parâmetros e todos os conectores da página. Rodar isso a cada tecla disputaria o frame com o canvas. Esperar 250ms depois da última alteração passa despercebido para quem digita e pesa muito menos.

▸ Clipboard assinadocanvas/clipboard.js

O que é copiado também vai para a área de transferência do sistema, como JSON com a assinatura papyrus/clipboard. É isso que permite colar elementos de uma página em outra, e até entre abas do navegador.

Existe um buffer interno como reserva, porque o navegador pode negar permissão de leitura do clipboard. E o paste tem ordem de prioridade: imagem primeiro, depois JSON assinado, e por último texto solto — que vira nota adesiva, útil ao trazer requisito de fora.

Integração e segurança

▸ Import dinâmico do @google-cloud/storageserver/lib/gcs.js

O pacote não vem instalado por padrão, para a ferramenta continuar leve e funcionando offline. O import acontece dentro da função, na hora do upload. Sem o pacote, a API responde 501 com o comando de instalação, em vez de o servidor sequer subir.

▸ A credencial nunca volta para o navegadorgcs.js + panels/settings.js

A chave privada é validada, gravada em arquivo próprio dentro de _system/ e referenciada por caminho — o gcs.json nunca carrega a chave. A API de configuração devolve apenas o booleano hasCredential.

A aba Configurações também não mostra nada sobre o servidor: nem caminho de pasta, nem sistema operacional, nem versão do runtime. O teste de conexão aceita a chave colada e ainda não salva, para dar para validar antes de gravar em disco.

▸ O navegador de diretórios foi removidoroutes/system.js

A importação acontece só por upload pelo navegador. O antigo navegador de pastas do sistema operacional e a importação por caminho absoluto foram retirados de propósito: com a ferramenta rodando em servidor compartilhado, os dois exporiam a estrutura de pastas do host para qualquer pessoa com acesso à interface.

▸ Export só para o bucket, sem downloadpanels/exporters.js

O contrato de coleta precisa de um endereço só, compartilhado e versionado. Um arquivo baixado na máquina de quem exportou vira cópia divergente no dia seguinte. Gravar em caminho de disco escolhido pelo usuário também não é opção, porque exporia o filesystem do servidor.

Pelo mesmo raciocínio, o escopo é sempre o workspace inteiro: exportar página isolada produzia contratos parciais circulando em paralelo, cada um dizendo uma coisa.

▸ Erro bloqueia o export, aviso nãopanels/exporters.js

O auditor lê todas as páginas do disco e valida uma a uma antes de liberar o botão, e fecha com a checagem que nenhuma página consegue fazer sozinha: event_id repetido entre páginas diferentes.

Só erro bloqueia. Aviso é coisa de mapa em andamento — sem squad definido, gatilho ainda não descrito — e travar por isso deixaria o export inalcançável justamente enquanto o trabalho está sendo feito.
